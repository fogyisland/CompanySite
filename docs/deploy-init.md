# 生产环境「未初始化状态」部署清单

> 目标：把站点部署成**全新未安装**状态，通过 `/setup` 向导建库、生成 `.env`、建表、创建首个管理员。
> 适用代码版本：本文件同批次的代码（含「数据库连接参数收口到 `.env`」那次改造）及其之后。
>
> **这份清单由你在服务器上执行。** 我没有服务器 SSH 凭据，也不持有生产 MySQL 的账号密码。
> 下文所有路径都用 `<站点目录>` 表示，按你实际的部署路径替换。

---

## 0. 相对旧版本，代码变了什么

| | 旧 | 新 |
|---|---|---|
| 数据库连接参数的存放处 | `.env` **和** `data/db-config.json` 两处并存 | **只有 `.env`** |
| 遗留 `data/db-config.json` | 会被读取、还会被写回 | 启动时**自动并入 `.env` 并删除** |
| 谁来建库 | 运维手工 `CREATE DATABASE` | **向导自己建**（不存在才建，已存在就直接用） |
| 「测试连接」 | 连到具体库（库还没建就报「未知数据库」） | 连到**服务器本身**（库还没建也测得通） |
| 向导的步骤 | 令牌 → 数据库 → 建表 → 管理员 → 完成 | 令牌 → 数据库 → 管理员 → **创建并完成** |
| 最后一步 | 三次独立请求 | **一次原子请求**（建库 → 写 `.env` → 建表 → 建管理员 → 销毁令牌） |

最后一条是刻意的：拆成多次请求会留下「配置写了但没装完」的中间态，
而安装状态的判定只看管理员是否存在 —— 中间态等于把闸门重新打开，
留出一个能被抢先建管理员接管站点的窗口。合成一次之后，
要么装完，要么只差最后一步重来（幂等）。

## 1. 先读这一段：两种口径，技术上不等价

你最初的要求是「生产换空库 + 移除 `.env`，走 `/setup` 向导」。落地时有两种做法，**代价不同**：

| | **口径 A（推荐）**：保留 `.env`，只清空 `DB_NAME` | **口径 B**：彻底移除 `.env` |
|---|---|---|
| 非受管键（`PAYPAL_WEBHOOK_ID` / `MCP_TOKEN` / `DB_COPY_ALLOWED_HOSTS` …） | ✅ **逐字保留** | ❌ **全部丢失**，必须手工补回 |
| `SESSION_SECRET` | ✅ 沿用旧值 → 不用全员重新登录 | ❌ 重新生成 → 所有人被登出 |
| `CRON_TOKEN` | ✅ 沿用旧值 → 外部 cron 调用不受影响 | ❌ 重新生成 → 外部 cron 令牌要同步更新 |
| 需要手工建库 | ❌ 不需要（向导建） | ❌ 不需要（向导建） |
| 需要手工写 `.env` | ❌ 不需要 | ❌ 不需要 |
| 额外动作 | 清空一行 | 移走 `.env` + **手工补回非受管键** |

**结论：走口径 A。** 同样得到「全新未安装」的站点状态，但不会丢配置、不会让全员登出。

### 口径 A 的正确写法：清空 `DB_NAME`，不是改成新库名

这一步很容易做错，**做错就卡住**。

| 写法 | 启动时会发生什么 | 结果 |
|---|---|---|
| `DB_NAME='新库名'`（新库还不存在） | 启动就连库 → MySQL 回「未知数据库」 | ❌ **向导被挡在门外**：这种错误不算「数据库不可用」，改配置与建库类操作会被拒绝（403），向导走不下去 |
| `DB_NAME=''`（清空） | 进程发现数据库参数不完整，**压根不建连接池** → 判定为「数据库当前不可用」 | ✅ 闸门放行 → 向导可用 → 最后一步自己把库建出来 |

差别在于「连不上」和「连得上但那个库不存在」被当成两件事：
前者是「站点是坏的，正需要向导来救」，后者是「状态判不出来」，必须保守拒绝。

**清空 `DB_NAME` 之后，站点是「不可用」而不是「已安装」** —— 这正是我们要的状态：
`/setup` 会出现，向导最后一步会把库名填回去。

### 两种口径都必须先处理的一件事：遗留的 `data/db-config.json`

那份 json 是旧版本留下的**第二处明文凭据副本**。新代码在启动时会把它的内容并入 `.env` 然后删掉它 ——

**但如果你想要的是「全新未安装」，就不能让这次迁移发生**，否则 `.env` 会被填回旧的库名，
站点连回旧库 → 旧库有管理员 → 判定「已安装」→ `/setup` 直接 302 到 `/login`，向导根本不出现。

所以：**先把那份 json 挪走（改名保留，别删）**，再启动新代码。

- 口径 A：`.env` 里有 `DB_HOST` → 启动时 json 会被直接删除（不覆盖 `.env`），这一步可以跳过；
  但如果你不确定 `.env` 存在，就按下面 4.2 节先挪走。
- 口径 B：`.env` 不存在 → 启动时 json 会被「恢复」成 `.env` → **必须先挪走**。

挪走前先把里面的连接参数**记下来**（它就是你现在正在用的库）：向导第 1 页要填这些值。

## 2. 先确认状态，再动手

### 2.1 「需要初始化」怎么判定

**唯一权威判据：`users` 表里 `is_admin = 1` 的行数。**

| 查库结果 | 判定 |
|---|---|
| `is_admin = 1` 的行数 **> 0** | **已安装** —— 不需要初始化 |
| `is_admin = 1` 的行数 **= 0** | **需要初始化** |
| `users` 表根本不存在 | **需要初始化** |

> 判定只看管理员行，**不看表建好了没有、不看默认数据灌了没有** —— 那两件事都是幂等的，
> 拿它们当闸门会在「表建好 → 管理员还没建」这个窗口期把闸门重新打开，别人能抢先建管理员接管站点。

**不碰库也能看的四个信号：**

| 信号 | 判「需要初始化」 |
|---|---|
| `GET /setup` 的响应 | **200** = 未安装；**302** 到 `/login` 或 `/admin-overview` = 已安装 |
| 首页 `/` 的响应 | **302 → /setup** = 未安装；**200** = 已安装 |
| `data/setup-token.txt` | **存在** = 未安装（或数据库不可达）；不存在 = 已安装 |
| 启动日志 | 出现「站点尚未完成安装，请打开 /setup 完成初始化」= 未安装 |

> `/setup` 在已安装状态下 **302 到 `/login` 是设计如此**，不是页面坏了 ——
> 它在防止一个已经装好的站点被重新初始化。

服务器上现在就能跑：

```bash
cd <站点目录>

# ① 令牌文件（未安装时才会生成）
ls -l data/setup-token.txt 2>/dev/null || echo "无令牌文件 → 大概率已安装"

# ② /setup 现在给什么
curl -s -o /dev/null -w '/setup: %{http_code} %{redirect_url}\n' https://www.booming.one/setup

# ③ 首页现在给什么
curl -s -o /dev/null -w '/     : %{http_code} %{redirect_url}\n' https://www.booming.one/

# ④ 权威判据（密码交互式输入）
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> \
  -e "SELECT COUNT(*) AS admins FROM users WHERE is_admin = 1;"
```

### 2.2 前置条件

- [ ] 服务器 SSH 可用
- [ ] 知道站点目录（下面用 `<站点目录>` 占位，按你的实际路径改）
- [ ] 有一个**能建库**的 MySQL 账号（向导最后一步要 `CREATE DATABASE`）——
      这一步只能你来确认；向导会在权限不足时给出明确提示
- [ ] 旧库不会被删，只是**保留**（本流程全程不碰旧库的数据）
- [ ] 浏览器能访问 `https://www.booming.one/setup`

## 4. 把站点切到「未配置」状态

### 4.1 记下当前配置（值不要贴进聊天/工单）

```bash
cd <站点目录>
grep -E '^(DB_HOST|DB_PORT|DB_USER|DB_NAME)=' .env
```

同时列出 `.env` 的全部键名，确认有没有需要保留的非受管键：

```bash
sed -E 's/=.*//' .env | grep -E '^[A-Z_][A-Z0-9_]*$'
```

### 4.2 挪走遗留的 `data/db-config.json`

```bash
cd <站点目录>
mv data/db-config.json "data/db-config.json.bak-${STAMP}" 2>/dev/null \
  || echo "（没有这个文件，跳过）"
```

> 先把它里面的连接参数记下来（向导第 1 页要用）。挪走而不是删 —— 万一要回滚还得靠它。

### 4.3 口径 A：清空 `DB_NAME`（推荐）

```bash
cd <站点目录>
sed -i "s|^DB_NAME=.*|DB_NAME=''|" .env

# 核对：DB_NAME 应该变成空的，其余没动
grep -E '^(DB_HOST|DB_PORT|DB_USER|DB_NAME)=' .env
```

> **不要**把 `DB_NAME` 改成一个还不存在的新库名 —— 见第 1 节的说明，那样向导会被 403 挡下。
> 必须是**空值**，让进程判定为「数据库未配置」。

### 4.4 口径 B：彻底移除 `.env`（如果你坚持）

⚠️ 这一节要做三件事，**少一件都达不到「未初始化状态」，或者会丢配置**。

```bash
cd <站点目录>

# ① 把「非受管键」的原始行搬出来（8 个受管键之外的全部保留）
grep -vE '^(PORT|SESSION_SECRET|CRON_TOKEN|DB_HOST|DB_PORT|DB_USER|DB_PASSWORD|DB_NAME)=' \
  ".env.bak-${STAMP}" > /tmp/preserved-env-keys.txt
cat /tmp/preserved-env-keys.txt      # 逐行确认，这就是之后要补回 .env 的内容

# ② 移走 .env
mv .env ".env.removed-${STAMP}"

# ③ 挪走遗留的 db-config.json（同 4.2）—— 不挪走的话，
#    启动时它会被迁移回 .env，站点连回旧库，判定「已安装」，/setup 直接 302。
mv data/db-config.json "data/db-config.json.bak-${STAMP}" 2>/dev/null || echo "（没有这个文件，跳过）"
```

装完之后把这些键**补回**新 `.env`（向导写出的 `.env` 里只有 8 个受管键）：

```bash
cat /tmp/preserved-env-keys.txt >> <站点目录>/.env
```

> 口径 B 下 `SESSION_SECRET` / `CRON_TOKEN` 也会变成新值：
> `SESSION_SECRET` 变 → 所有已登录会话失效（可接受）；
> `CRON_TOKEN` 变 → **任何外部定时任务调 `/api/cron/*` 的地方都要同步更新令牌**，否则静默失败。

## 5. 拉代码、装依赖、重启

```bash
cd <站点目录>
git pull origin main
npm install --production
pm2 restart booming
```

启动日志里**应该**看到数据库初始化失败（这是预期的 —— 我们就是要它处于「未配置」状态）：

```
  ✖ 数据库初始化失败: 未配置数据库连接参数（.env 缺少 DB_HOST / DB_USER / DB_NAME）—— 请打开 /setup 完成初始化
    服务以降级模式启动：/setup 安装向导可用，其余依赖数据库的接口返回 503。
```

以及安装令牌提示（**这一段说明站点已被判定为「未安装 / 数据库不可用」，状态正确**）：

```
  ╔══════════════════════════════════════════════════════╗
  ║  站点尚未完成安装，请打开 /setup 完成初始化            ║
  ╚══════════════════════════════════════════════════════╝
  安装令牌: <48位十六进制>
  令牌文件: <站点目录>/data/setup-token.txt
```

> 令牌**不会**出现在任何 HTTP 响应里，只在服务器控制台和 `data/setup-token.txt`。
> 取令牌：`cat <站点目录>/data/setup-token.txt`

如果日志里出现的是「MySQL连接成功」，说明 `.env` 里还有能连上的库名 —— 站点仍连着旧库，
回到 4.3 重新清空 `DB_NAME`。

## 6. 走 /setup 向导

浏览器打开 **https://www.booming.one/setup**，输入上面第 5 节日志里取到的令牌。

步骤条：**安装令牌 → 数据库 → 管理员 → 完成**。

### 第 0 步 · 校验安装令牌

粘贴令牌 → 「校验并继续」。令牌错误会直接报出来；站点已安装时会提示并跳转到登录页。

### 第 1 步 · 数据库连接

| 字段 | 口径 A 应显示 | 说明 |
|---|---|---|
| 主机 | `<DB_HOST>` | 与旧 `.env` 相同（自动预填） |
| 端口 | `<DB_PORT>` | 通常 3306 |
| 用户 | `<DB_USER>` | 必须是**能建库**的那个账号 |
| 密码 | 留空 | 下方提示「留空表示沿用已保存的密码」—— 界面不回显密码 |
| **数据库名** | **空的**（要自己填） | 填新库名，例如 `booming_init` |

> 库名规则：**只能含字母、数字、下划线、连字符，且必须以字母或下划线开头**，不超过 64 字符。
> 前端会当场拦下不合法的名字。

点「**测试连接**」：连的是**服务器本身**，所以目标库还不存在也测得通。
返回信息会明确告诉你「数据库 X 不存在，最后一步会创建它」还是「已存在，将直接使用」。

点「**下一步**」会先自动测一次连接 —— 不用刻意先点测试。

### 第 2 步 · 管理员账号

填用户名（3~32 位，字母/数字/下划线/点/连字符）/ 密码（≥8 位且同时含字母和数字）/ 邮箱（可选）。

### 第 3 步 · 创建数据库并完成初始化

页面先给一张汇总表（主机、库名、数据库用户、管理员账号、邮箱）让你核对，**确认无误再点**
「创建数据库并完成初始化」。

这一次点击会**一个请求**做完：

1. 测服务器连通性
2. 建库（不存在才建，已存在直接用）
3. 把连接参数写进 `.env`（同时生成 `SESSION_SECRET` / `CRON_TOKEN`，权限 0600）
4. 切换连接池 → 建表 + 灌默认数据
5. 创建首个管理员
6. 销毁安装令牌

成功后页面显示「初始化完成」，并提示**重启一次服务**：

```bash
cd <站点目录>
pm2 restart booming
```

> 不重启的话，`.env` 里的连接参数虽然已经当场生效，但**会话签名密钥与 session 存储池**
> 是在进程启动时绑定的 —— 重启后旧密钥失效、存储池还可能指向旧库。重启后重新登录一次即可。

中途失败可以**原地重试**（幂等）：
- 表没建成功 → 判定仍是「未安装」→ 闸门放行 → 直接再点一次；
- 管理员用户名冲突 → 管理员行数仍为 0 → 闸门放行 → 换个用户名再点。

> 只有「连不上 / 认证不过」这一类错误会**回滚 `.env`** —— 那种情况配置本身就是错的，
> 留着它等于让站点下次启动就带着坏配置。表结构 / 权限类错误**不回滚**：
> 配置是对的，回滚只会让你白填一遍。

## 7. 验证清单

**安装前**（重启之后、走向导之前）—— 站点应处于「未初始化」状态：

```bash
# ① 首页 302 跳 /setup（未安装闸门）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/
#    期望：302 https://www.booming.one/setup

# ② /setup 可达
curl -s -o /dev/null -w '%{http_code}\n' https://www.booming.one/setup
#    期望：200
```

> 若 ① 返回 200 而不是 302，说明站点**仍被判为「已安装」** → 第 4 节的 `DB_NAME` 没清空成功，
> 或新库里已经有管理员行。回服务器核对后重来。

**安装后**：

```bash
# ③ 首页恢复 200（不再是 302）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/
#    期望：200

# ④ 安装接口已关闭
curl -s https://www.booming.one/api/setup/status -H 'X-Setup-Token: <无效令牌>' -w '\n%{http_code}\n'
#    期望：403（安装完成时令牌文件已被销毁，安装接口永久关闭）

# ⑤ 日志无报错
pm2 logs booming --lines 50
```

浏览器侧再确认：用新管理员登录 `https://www.booming.one/login` → `/admin-overview` 能打开；
首页正常渲染、Logo/主题/设置项都正常；**产品列表为空**（新库没有业务数据）；
后台「系统设置 → 数据库」显示的库名是你刚填的那个。

再确认一次「配置只有一处」：

```bash
cd <站点目录>
ls -l data/db-config.json 2>/dev/null && echo "⚠ 还在" || echo "✓ 遗留配置已清理"
```

## 8. 回滚

**旧库的数据全程没被碰过**，所以回滚只是把 `.env` 指回去：

```bash
cd <站点目录>
cp -a ".env.bak-${STAMP}" .env
pm2 restart booming
```

回滚后站点指向旧库，`SESSION_SECRET` / `CRON_TOKEN` 也一并还原（口径 A 下本来就是同一份），
不需要额外操作。新建的空库留着不删即可。

如果走的是口径 B，还要把非受管键补回来（4.4 节已经处理过，这里只需确认 `.env` 里还在）。

### 如果在旧库上误建了管理员

只有一种情况会污染旧库：向导第 1 步把库名填成了旧库名，然后点「创建并完成」——
但这种情况在口径 A 下不会发生（`DB_NAME` 已清空，旧库根本不在配置里）。
万一真发生了，后果是：旧库里可能多出一个管理员（用户名相同会被拒）。
处理办法是去旧库删掉那一行用户记录。旧库的业务数据没有丢失风险，
要核对就用第 3 节那份 `mysqldump` 备份对照。

## 9. 后续要单独处理的两件事

1. **新库是空的**：产品、新闻、公告、定价档位等业务数据都不在。旧库导数据到新库要走
   后台「系统设置 → 数据库」的导出/导入功能（`/api/db-export` / `/api/db-import`），
   注意 `db.updateProduct` 是全列覆盖，导入后要抽查。
2. **支付回调**（口径 B 才需要）：`PAYPAL_WEBHOOK_ID` 等键必须已按 4.4 节补回 `.env` 并重启，
   否则 PayPal 回调会静默失效 —— 订单状态永远停在待支付。
