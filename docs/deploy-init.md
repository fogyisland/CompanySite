# 生产环境部署清单：升级存量站点 / 全新初始化

> 目标：
>
> - **场景一（存量站点升级）** —— 把已经在跑的站点升到本版本，并且**不被误判成「未初始化」**。
> - **场景二（全新部署）** —— 把站点部署成全新未初始化状态，通过 `/init` 向导建库、生成 `.env`、
>   建表、创建首个管理员。
>
> 适用代码版本：本文件同批次的代码及其之后。
>
> **这份清单由你在服务器上执行。** 我没有服务器 SSH 凭据，也不持有生产 MySQL 的账号密码。
> 下文所有路径都用 `<站点目录>` 表示，按你实际的部署路径替换。

---

## 0. 相对旧版本，代码变了什么

| | 旧 | 新 |
|---|---|---|
| 数据库连接参数的存放处 | `.env` **和** `data/db-config.json` 两处并存 | **只有 `.env`** |
| 遗留 `data/db-config.json` | 会被读取、还会被写回 | **不再自动接管** —— 启动时既不读它也不删它，要手工搬 |
| 启动时会不会做初始化 | 会自动建表、灌种子 | **不做** —— 全新站点的表结构、默认数据、管理员全部由 `/init` 向导一次做完 |
| 「站点是否已初始化」的判据 | `users` 表里有 `is_admin=1` | **双保险**：`.env` 里 `INITIALIZED=True` **且** `users` 表里有 `is_admin=1` |
| 谁来建库 | 运维手工 `CREATE DATABASE` | **向导自己建**（不存在才建，已存在就直接用） |
| 「测试连接」 | 连到具体库（库还没建就报「未知数据库」） | 连到**服务器本身**（库还没建也测得通） |
| 向导的步骤 | 令牌 → 数据库 → 建表 → 管理员 → 完成 | 数据库 → 管理员 → 网站设定 → **执行初始化**（无令牌） |
| 最后一步 | 三次独立请求 | **一次原子请求**（建库 → 写 `.env` → 建表 → 建管理员 → 写网站设定 → 写 `INITIALIZED=True`） |
| 未初始化时静态直出的 HTML 页面 | **200**（首页返回空壳，API 全 503） | **302 → /init**（静态资源仍 200） |

其中两条变化最要紧，单独拎出来说：

1. **启动时不再做初始化。** 全新站点的表结构、默认数据、管理员账号，全部由 `/init` 向导一次做完。
   唯一保留的是**已初始化站点的表结构维护**（幂等补列 + 补种子）—— 那是升级路径，不是初始化。
2. **判定多了一环「`.env` 标志」。** 存量站点升级时如果忘了在 `.env` 里补一行 `INITIALIZED=True`，
   站点会被判定成「未初始化」，全站跳转到 `/init`，Init 接口也会重新打开。
   服务启动时会在控制台打印醒目告警提示这件事，但**告警不能代替操作**。

## 1. 场景一：存量站点升级（先做这一节）

已经在跑的站点升级到本版本，**只需要动 `.env`**。不用改代码、不用重装依赖。

### 1.1 为什么要动

新的判定是**双保险**：

```
已初始化 = .env 里 INITIALIZED=True
         AND users 表里有 is_admin=1 的账号
```

老站点的 `.env` 里没有 `INITIALIZED` 这一行 —— 判定链的第一环不成立，
站点就会被当成「没初始化过」：全站跳转 `/init`，Init 接口重新打开。
（第二环还在，所以**不会**出「被抢先建管理员」的事，但用户看到的是「站点炸了」。）

### 1.2 怎么做

```bash
cd <站点目录>

# ① 备份 .env（可跳过，但改配置前备份一次总没坏处）
STAMP=$(date +%Y%m%d-%H%M%S)
cp -a .env ".env.bak-${STAMP}"

# ② 补标志 —— 已经有了就跳过这步
grep -qE '^INITIALIZED=' .env \
  || printf '\nINITIALIZED=True\n' >> .env

# ③ 确认结果（只看键名和这个标志的值，不回显密码）
grep -E '^INITIALIZED=' .env
```

> 这一行**必须在重启服务之前补上**。先重启再补，中间那段时间站点是「未初始化」状态，
> 用户会撞到跳转。

### 1.3 遗留的 `data/db-config.json`

新代码**不再自动接管**那份 json —— 启动时既不读它也不删它。

它里面有明文密码、权限 0644（比 `.env` 的 0600 差一档），留着等于把生产凭据又复制了一份。

**第一步：把里面的 `DB_*` 写进真的 `.env`。** 两条路都行，写的是同一个文件、走的是同一条落盘路径：

| | 怎么做 | 注意 |
|---|---|---|
| **A（推荐）** | 登录后台 →「系统设置 → 数据库」→ 照着 json 填一遍 → 保存 | 保存走的是和 Init 向导同一条落盘路径（写 `.env`、备份 `.env.bak`、当场切换连接池、连不上自动回滚）。密码框显示成 `******` 时**留空不动**就会保留原密码 |
| B | 直接编辑 `.env`，把 `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` 补齐 | 手改没有回滚保护，改错了要自己改回来 |

> 新版本的默认约定是「仓库只留 `.env.example`，真正的 `.env` 由应用自己写」。
> 所以**不要**去写什么一次性迁移脚本 —— 应用本来就有现成的写入通路，
> 用它反而能顺带做连接测试与回滚。

确认 `.env` 里已经有完整的 `DB_*` 之后，把那份 json 挪走（改名保留，别直接删 —— 万一要回滚还得靠它）：

```bash
cd <站点目录>
mv data/db-config.json "data/db-config.json.bak-${STAMP}" 2>/dev/null \
  || echo "（没有这个文件，跳过）"
```

### 1.4 重启并验证

```bash
cd <站点目录>
git pull origin main
npm install --production
pm2 restart booming
```

> ⚠️ **`git pull` 不等于生效，必须重启进程。**
> 静态文件（HTML / CSS / JS）是每次请求现读磁盘的 —— pull 完刷新页面就能看到新样式；
> 而 API 逻辑是**进程启动时加载进内存**的 —— 不重启就还是老逻辑。
> 两边不同步的结果是一个很容易误判的混合状态：
> **页面长得像新的、接口行为却像旧的**（例如旧代码报「令牌不正确」，而新代码里压根没有令牌这回事）。
> 判断有没有生效，看接口而不是看页面：
> `curl -s https://www.booming.one/api/init/status` —— 返回 200 + JSON 状态就是新代码在跑。

启动日志里**不应该**出现下面这段（出现了就说明 1.2 节没做对）：

```
  ⚠ 数据库里已有管理员账号，但 .env 里没有 INITIALIZED=True。
    站点会被判定为「未初始化」，全站将跳转到 /init，Init 接口也会打开。
    请在 .env 里补一行 INITIALIZED=True 后重启服务。
```

验证：

```bash
# 首页正常（不是 302）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/
#    期望：200（没有 redirect_url）

# /init 对已初始化的站点会 302 到登录页（设计如此，防重新初始化）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/init
```

> 判定为「未初始化」时，**不只是首页**，所有静态直出的 HTML 页面都会被 302 到 `/init`
> （CSS / JS 等静态资源照常 200 —— 页面本身要靠它们渲染）。
> 这一层是为了让故障现场不被误判：否则首页会返回 200 + 空壳 HTML，
> 看着「页面能打开」就以为站点正常，实际里面的 API 全是 503。
>
> 所以补标志没补上时，你会看到**整站页面**都在跳 `/init`，而不只是 `/`。

## 2. 场景二：全新部署

### 2.1 先读这一段：两种口径，技术上不等价

要求是「生产换空库 + 移除 `.env`，走 `/init` 向导」。落地时有两种做法，**代价不同**：

| | **口径 A（推荐）**：保留 `.env`，只清空 `DB_NAME` | **口径 B**：彻底移除 `.env` |
|---|---|---|
| 非受管键（`PAYPAL_WEBHOOK_ID` / `MCP_TOKEN` / `DB_COPY_ALLOWED_HOSTS` …） | ✅ **逐字保留** | ❌ **全部丢失**，必须手工补回 |
| `SESSION_SECRET` | ✅ 沿用旧值 → 不用全员重新登录 | ❌ 重新生成 → 所有人被登出 |
| `CRON_TOKEN` | ✅ 沿用旧值 → 外部 cron 调用不受影响 | ❌ 重新生成 → 外部 cron 令牌要同步更新 |
| 需要手工建库 | ❌ 不需要（向导建） | ❌ 不需要（向导建） |
| 需要手工写 `.env` | ❌ 不需要 | ❌ 不需要 |
| 额外动作 | 清空一行 | 移走 `.env` + **手工补回非受管键** |

**结论：走口径 A。** 同样得到「全新未初始化」的站点状态，但不会丢配置、不会让全员登出。

### 2.2 口径 A 的正确写法：清空 `DB_NAME`，不是改成新库名

这一步很容易做错，**做错就卡住**。

| 写法 | 启动时会发生什么 | 结果 |
|---|---|---|
| `DB_NAME='新库名'`（新库还不存在） | 启动就连库 → MySQL 回「未知数据库」 | ❌ **向导被挡在门外**：这种错误不算「数据库不可用」，改配置与建库类操作会被拒绝（403），向导走不下去 |
| `DB_NAME=''`（清空） | 进程发现数据库参数不完整，**压根不建连接池** → 判定为「数据库当前不可用」 | ✅ 闸门放行 → 向导可用 → 最后一步自己把库建出来 |

差别在于「连不上」和「连得上但那个库不存在」被当成两件事：
前者是「站点是坏的，正需要向导来救」，后者是「状态判不出来」，必须保守拒绝。

**清空 `DB_NAME` 之后，站点是「不可用」而不是「已初始化」** —— 这正是我们要的状态：
`/init` 会出现，向导最后一步会把库名填回去。

> 顺带一提：`INITIALIZED` 这一行在口径 A 下**保持 `True` 即可**，不需要动它。
> 向导走完最后一步会把它重新写成 `True`，中途失败重跑也一样（幂等）。

### 2.3 遗留的 `data/db-config.json`

那份 json 是旧版本留下的**第二处明文凭据副本**。新代码不会自动迁移它 ——

**但如果它还在，站点启动后仍会连回旧库**（因为 `.env` 里已经清空了 `DB_NAME`，
而新代码压根不读那份 json，所以这倒不会坏事 —— 只是那份文件还在而已）。

**要处理的是它里面的凭据副本**：确认 `.env` 里的 `DB_*` 齐全之后，把它挪走（改名保留）。
向导第 1 页要填的连接参数，就是你现在正在用的那套 —— 挪走前先记下来。

## 3. 先确认状态，再动手

### 3.1 「需要初始化」怎么判定

**双保险判据，两条都要满足才算「已初始化」：**

| 查库结果 | `.env` 里的 `INITIALIZED` | 判定 |
|---|---|---|
| `is_admin = 1` 的行数 > 0 | `True` | **已初始化** —— 不需要初始化 |
| `is_admin = 1` 的行数 > 0 | 缺失 / `False` | **需要初始化**（老站点升级的典型状态） |
| `is_admin = 1` 的行数 = 0 | 任意 | **需要初始化** |
| `users` 表根本不存在 | 任意 | **需要初始化** |

> 判定只看管理员行与标志，**不看表建好了没有、不看默认数据灌了没有** —— 那两件事都是幂等的，
> 拿它们当闸门会在「表建好 → 管理员还没建」这个窗口期把闸门重新打开，别人能抢先建管理员接管站点。

**不碰库也能看的几个信号：**

| 信号 | 判「需要初始化」 |
|---|---|
| `GET /init` 的响应 | **200** = 未初始化；**302** 到 `/login` 或 `/admin-overview` = 已初始化 |
| 首页 `/` 的响应 | **302 → /init** = 未初始化；**200** = 已初始化 |
| 其他 HTML 页面（如 `/news.html`） | **302 → /init** = 未初始化；**200** = 已初始化 |
| `data/init-token.txt` | 已移除 —— 该文件不再生成，判断初始化状态改用下两行 |
| 启动日志 | 出现「站点尚未完成初始化，请打开 /init 继续」= 未初始化 |

> `/init` 在已初始化状态下 **302 到 `/login` 是设计如此**，不是页面坏了 ——
> 它在防止一个已经装好的站点被重新初始化。
>
> HTML 页面同样被拦（CSS / JS 等静态资源不拦）：静态文件由 `express.static` 直出，
> 不管它的话未初始化的首页会返回 200 + 空壳 HTML，看着「页面能打开」实际 API 全是 503。

服务器上现在就能跑：

```bash
cd <站点目录>

# ① .env 里的标志（只看这一行，不回显密码）
grep -E '^INITIALIZED=' .env || echo "没有 INITIALIZED 这一行 → 需要补"

# ② /init 现在给什么
curl -s -o /dev/null -w '/init: %{http_code} %{redirect_url}\n' https://www.booming.one/init

# ③ 首页现在给什么
curl -s -o /dev/null -w '/     : %{http_code} %{redirect_url}\n' https://www.booming.one/

# ④ 判据的一半（另一半是上面的 INITIALIZED）
mysql -h <DB_HOST> -P <DB_PORT> -u <DB_USER> -p <DB_NAME> \
  -e "SELECT COUNT(*) AS admins FROM users WHERE is_admin = 1;"
```

### 3.2 前置条件

- [ ] 服务器 SSH 可用
- [ ] 知道站点目录（下面用 `<站点目录>` 占位，按你的实际路径改）
- [ ] 有一个**能建库**的 MySQL 账号（向导最后一步要 `CREATE DATABASE`）——
      这一步只能你来确认；向导会在权限不足时给出明确提示
- [ ] 旧库不会被删，只是**保留**（本流程全程不碰旧库的数据）
- [ ] 浏览器能访问 `/init`

## 5. 把站点切到「未配置」状态

### 5.1 记下当前配置（值不要贴进聊天/工单）

```bash
cd <站点目录>
grep -E '^(DB_HOST|DB_PORT|DB_USER|DB_NAME)=' .env
```

同时列出 `.env` 的全部键名，确认有没有需要保留的非受管键：

```bash
sed -E 's/=.*//' .env | grep -E '^[A-Z_][A-Z0-9_]*$'
```

### 5.2 挪走遗留的 `data/db-config.json`

```bash
cd <站点目录>
mv data/db-config.json "data/db-config.json.bak-${STAMP}" 2>/dev/null \
  || echo "（没有这个文件，跳过）"
```

> 先把它里面的连接参数记下来（向导第 1 页要用）。挪走而不是删 —— 万一要回滚还得靠它。

### 5.3 口径 A：清空 `DB_NAME`（推荐）

```bash
cd <站点目录>
sed -i "s|^DB_NAME=.*|DB_NAME=''|" .env

# 核对：DB_NAME 应该变成空的，其余没动
grep -E '^(DB_HOST|DB_PORT|DB_USER|DB_NAME)=' .env
```

> **不要**把 `DB_NAME` 改成一个还不存在的新库名 —— 见 2.2 节的说明，那样向导会被 403 挡下。
> 必须是**空值**，让进程判定为「数据库未配置」。

### 5.4 口径 B：彻底移除 `.env`（如果你坚持）

⚠️ 这一节要做三件事，**少一件都达不到「未初始化状态」，或者会丢配置**。

```bash
cd <站点目录>

# ① 把「非受管键」的原始行搬出来（受管键之外的全部保留）
grep -vE '^(PORT|SESSION_SECRET|CRON_TOKEN|DB_HOST|DB_PORT|DB_USER|DB_PASSWORD|DB_NAME|INITIALIZED)=' \
  ".env.bak-${STAMP}" > /tmp/preserved-env-keys.txt
cat /tmp/preserved-env-keys.txt      # 逐行确认，这就是之后要补回 .env 的内容

# ② 移走 .env
mv .env ".env.removed-${STAMP}"

# ③ 挪走遗留的 db-config.json（同 5.2）
mv data/db-config.json "data/db-config.json.bak-${STAMP}" 2>/dev/null || echo "（没有这个文件，跳过）"
```

装完之后把这些键**补回**新 `.env`（向导写出的 `.env` 里只有受管键）：

```bash
cat /tmp/preserved-env-keys.txt >> <站点目录>/.env
```

> 口径 B 下 `SESSION_SECRET` / `CRON_TOKEN` 也会变成新值：
> `SESSION_SECRET` 变 → 所有已登录会话失效（可接受）；
> `CRON_TOKEN` 变 → **任何外部定时任务调 `/api/cron/*` 的地方都要同步更新令牌**，否则静默失败。

## 6. 拉代码、装依赖、重启

```bash
cd <站点目录>
git pull origin main
npm install --production
pm2 restart booming
```

> ⚠️ **别只 pull 不重启** —— 静态文件是现读磁盘的（刷新就能看到新样式），
> API 逻辑是进程启动时加载的（不重启还是老行为）。
> 两者不同步会呈现为「页面是新的、报错是旧的」，很容易误判成代码没推上去。
> 验证口径：**看接口，不看页面** —— `curl -s https://www.booming.one/api/init/status`
> 返回 200 + JSON 状态，说明新代码已经在跑。

启动日志里**应该**看到数据库连接失败（这是预期的 —— 我们就是要它处于「未配置」状态）：

```
  ✖ 数据库连接失败: 未配置数据库连接参数（.env 缺少 DB_HOST / DB_USER / DB_NAME）—— 请打开 /init 完成初始化
    服务以降级模式启动：/init 向导可用，其余依赖数据库的接口返回 503。
```

以及初始化提示（**这一段说明站点已被判定为「未初始化 / 数据库不可用」，状态正确**）：

```
  ╔══════════════════════════════════════════════════════╗
  ║  站点尚未完成初始化，请打开 /init 继续               ║
  ╚══════════════════════════════════════════════════════╝
```

> 初始化**不再需要令牌**：不生成 `data/init-token.txt`，不读 `INIT_TOKEN` / `SETUP_TOKEN`，
> 也没有令牌校验这一步。打开 `/init` 就是第 1 页。

如果日志里出现的是「MySQL连接成功」，说明 `.env` 里还有能连上的库名 —— 站点仍连着旧库，
回到 5.3 重新清空 `DB_NAME`。

## 7. 走 /init 向导

浏览器打开站点的 `/init`，直接进入第 1 页。

步骤条：**数据库 → 管理员 → 网站设定 → 初始化**。

### 第 1 步 · 数据库连接

| 字段 | 口径 A 应显示 | 说明 |
|---|---|---|
| 主机 | `<DB_HOST>` | 与旧 `.env` 相同（自动预填） |
| 端口 | `<DB_PORT>` | 通常 3306 |
| 用户 | `<DB_USER>` | 必须是**能建库**的那个账号 |
| 密码 | 留空 | 下方提示「留空表示沿用已保存的密码」—— 界面不回显密码 |
| **数据库名** | **空的**（要自己填） | 填新库名，例如 `booming_init` |

> 库名规则：**只能含字母、数字、下划线、连字符，且必须以字母或下划线开头**，不超过 64 字符。
> 前端会当场拦下不合法的名字。

点「**测试连接**」：连的是**服务器本身**，所以目标库还不存在也测得通。
返回信息会明确告诉你「数据库 X 不存在，最后一步会创建它」还是「已存在，将直接使用」。

点「**下一步**」会先自动测一次连接 —— 不用刻意先点测试。

### 第 2 步 · 管理员账号

填用户名（3~32 位，字母/数字/下划线/点/连字符）/ 密码（≥8 位且同时含字母和数字）/ 邮箱（可选）。

### 第 3 步 · 网站设定

填站点名称（不能为空，最多 255 个字符），可选上传 Logo：

- 支持 png / jpg / gif / webp，最大 2MB；
- 上传后由服务端重新命名并落盘，文件名固定为 `logo.扩展名`；
- Logo 可以留空 —— 之后随时能在后台「系统设置」里改。

### 第 4 步 · 执行初始化

页面先给一张汇总表（主机、库名、数据库用户、管理员账号、邮箱、站点名称）让你核对，
**确认无误再点**「开始初始化」。

这一次点击会**一个请求**做完：

1. 测服务器连通性
2. 建库（不存在才建，已存在直接用）
3. 把连接参数写进 `.env`（同时生成 `SESSION_SECRET` / `CRON_TOKEN`，权限 0600）
4. 切换连接池 → 建表 + 灌默认数据
5. 创建首个管理员
6. 写入网站设定（站点名称 + Logo）
7. 写入 `INITIALIZED=True`

执行过程中每完成一步，页面上的「初始化过程」清单会把对应条目标成已完成；
中途失败会把卡住的那一步标红，可以原地重试。

成功后页面显示「初始化完成」，并提示**重启一次服务**：

```bash
cd <站点目录>
pm2 restart booming
```

> 不重启的话，`.env` 里的连接参数虽然已经当场生效，但**会话签名密钥与 session 存储池**
> 是在进程启动时绑定的 —— 重启后旧密钥失效、存储池还可能指向旧库。重启后重新登录一次即可。

中途失败可以**原地重试**（幂等）：
- 表没建成功 → 判定仍是「未初始化」→ 闸门放行 → 直接再点一次；
- 管理员用户名撞上一个**已经是管理员**的账号 → 跳过创建，直接把标志补上；
- 管理员用户名撞上一个**普通用户** → 换个用户名再点。

> **库里已经有管理员时，不许用新用户名再造一个** —— 向导会返回 409 并提示。
> 这不是限制你的自由度，是防止「运行中的站点被随便塞管理员」。
> 恢复办法只有两个：第 2 步填你现有的管理员用户名（跳过创建，只补标志），
> 或直接手工在 `.env` 里补一行 `INITIALIZED=True` 后重启。

> 只有「连不上 / 认证不过」这一类错误会**回滚 `.env`** —— 那种情况配置本身就是错的，
> 留着它等于让站点下次启动就带着坏配置。表结构 / 权限类错误**不回滚**：
> 配置是对的，回滚只会让你白填一遍。

## 8. 验证清单

**初始化前**（重启之后、走向导之前）—— 站点应处于「未初始化」状态：

```bash
# ① 首页 302 跳 /init（未初始化闸门）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/
#    期望：302 https://www.booming.one/init

# ② /init 可达
curl -s -o /dev/null -w '%{http_code}\n' https://www.booming.one/init
#    期望：200

# ③ 其他 HTML 页面同样被拦（静态直出的页面也走闸门）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/news.html
#    期望：302 https://www.booming.one/init

# ④ 静态资源照常提供（页面要靠它们渲染，不能一起拦掉）
curl -s -o /dev/null -w '%{http_code}\n' https://www.booming.one/css/pages/init.css
#    期望：200
```

> 若 ① 返回 200 而不是 302，说明站点**仍被判为「已初始化」** → 第 5 节的 `DB_NAME` 没清空成功，
> 或新库里已经有管理员行。回服务器核对后重来。

**初始化后**：

```bash
# ⑤ 首页恢复 200（不再是 302）
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://www.booming.one/
#    期望：200

# ⑥ Init 接口已关闭
curl -s https://www.booming.one/api/init/status -w '\n%{http_code}\n'
#    期望：403（初始化完成后 Init 接口永久关闭）

# ⑦ 日志无报错
pm2 logs booming --lines 50
```

浏览器侧再确认：用新管理员登录 `/login` → `/admin-overview` 能打开；
首页正常渲染、Logo/主题/设置项都正常；**产品列表为空**（新库没有业务数据）；
后台「系统设置 → 数据库」显示的库名是你刚填的那个。

再确认一次「配置只有一处」：

```bash
cd <站点目录>

# ① 标志写进去了
grep -E '^INITIALIZED=' .env
#    期望：INITIALIZED=True

# ② 遗留配置已清理
ls -l data/db-config.json 2>/dev/null && echo "⚠ 还在" || echo "✓ 遗留配置已清理"
```

## 9. 回滚

**旧库的数据全程没被碰过**，所以回滚只是把 `.env` 指回去：

```bash
cd <站点目录>
cp -a ".env.bak-${STAMP}" .env
pm2 restart booming
```

回滚后站点指向旧库，`SESSION_SECRET` / `CRON_TOKEN` 也一并还原（口径 A 下本来就是同一份），
不需要额外操作。新建的空库留着不删即可。

> 回滚到旧 `.env` 时记得确认它里面有没有 `INITIALIZED=True` —— 没有的话，
> 站点会被判成「未初始化」，全站跳 `/init`（这是第 1 节讲过的那件事）。

如果走的是口径 B，还要把非受管键补回来（5.4 节已经处理过，这里只需确认 `.env` 里还在）。

### 如果在旧库上误建了管理员

只有一种情况会污染旧库：向导第 1 步把库名填成了旧库名，然后点「开始初始化」——
但这种情况在口径 A 下不会发生（`DB_NAME` 已清空，旧库根本不在配置里）。
万一真发生了，后果是：旧库里可能多出一个管理员（用户名相同会被拒）。
处理办法是去旧库删掉那一行用户记录。旧库的业务数据没有丢失风险，
要核对就用第 4 节那份 `mysqldump` 备份对照。

## 10. 后续要单独处理的两件事

1. **新库是空的**：产品、新闻、公告、定价档位等业务数据都不在。旧库导数据到新库要走
   后台「系统设置 → 数据库」的导出/导入功能（`/api/db-export` / `/api/db-import`），
   注意导入是全列覆盖，导入后要抽查。
2. **支付回调**（口径 B 才需要）：`PAYPAL_WEBHOOK_ID` 等键必须已按 5.4 节补回 `.env` 并重启，
   否则 PayPal 回调会静默失效 —— 订单状态永远停在待支付。
