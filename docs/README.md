## Init 向导（首次部署用）

站点「初始化完没有」是**双保险**判定，两个条件必须同时成立：

1. `.env` 里有 `INITIALIZED=True` —— 初始化完成时由向导写进去的标志；
2. `users` 表里有 `is_admin = 1` 的账号 —— 管理员确实存在。

单看①不行 —— `.env` 会被复制、被手工改，一旦被复制到另一台机器，
单靠标志会把一台空站点的 Init 接口永久关死。
单看②也不行 —— 建表与灌默认数据都是幂等的，「表建好了但管理员还没创建」的窗口期内，
Init 闸门会重新打开。

> `is_admin` 这一列是判据的前提。老库若当初建表时没有它，启动时的幂等补列
> （`db.js` 的 `userAlterStatements`）会补上；补不上时状态判定会退化成「无法判定」，
> Init 写操作一律 fail-closed —— 表现就是全新初始化卡在「建不出第一个管理员」。

向导页面：`GET /init`（未初始化时可用；已完成会跳转到 `/login` 或 `/admin-overview`）。

两道闸：

1. **「确实未初始化」判定** —— DB 异常时 fail-closed，拒绝写操作。
   例外范围见下面「数据库不可用时怎么办」。
2. 首个管理员创建成功、且 `INITIALIZED=True` 写入 `.env` 之后，**Init 接口永久关闭**。

> **Init 令牌机制已整体移除**：不再生成 `data/init-token.txt`，不再读取 `INIT_TOKEN` /
> `SETUP_TOKEN`，也没有 `/api/init/verify-token`。打开 `/init` 就能直接开始。
>
> 由此带来的取舍是明确的：**站点未初始化期间，任何能访问 `/init` 的人都可以完成初始化**
> （包括拿到管理员账号）。唯一的边界是「装好之后永久关闭」。
> 因此未初始化阶段的部署要么不暴露公网，要么由反向代理临时拦掉 `/init`，
> 初始化完成后再撤掉拦截。

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/api/init/status` | 未初始化 | 查询初始化状态（是否已完成、缺哪些表、配置来源、标志状态） |
| POST | `/api/init/test-db` | 未初始化 | 用提交的连接信息测试**服务器**连通性（不选具体库，库还没建也能测） |
| POST | `/api/init/upload-logo` | 未初始化 | 上传站点 Logo（限 2MB，png / jpg / gif / webp），返回站内路径 |
| POST | `/api/init/complete-install` | 未初始化 | **一次性完成初始化**：建库 → 写 `.env` → 建表 → 建管理员 → 写网站设定 → 写 `INITIALIZED=True` |
| POST | `/api/init/save-db-config` | 未初始化 | 只把连接参数**写进 `.env`** 并立即切换连接池（不建库、不建表） |
| POST | `/api/init/init-db` | 未初始化 | 建表 + 补列 + 灌默认数据（幂等，可重复执行） |
| POST | `/api/init/create-admin` | 未初始化 | 创建首个管理员 |

向导页面是**四页**结构：

1. **数据库** —— 填主机 / 端口 / 用户 / 密码 / 库名，「测试连接」连的是**服务器本身**，
   所以目标库还不存在也测得通。
2. **管理员** —— 填首个管理员的用户名、密码、邮箱。
3. **网站设定** —— 填站点名称，可选上传 Logo（上传后由服务端重新命名并落盘）。
4. **执行初始化** —— 汇总确认后点一次按钮，服务端按
   「建库 → 写 `.env` → 建表 + 灌默认数据 → 建管理员 → 写网站设定 → 写 `INITIALIZED=True`」
   的顺序做完，并把每一步的结果回传给页面渲染成进度清单。

第 4 步只发**一次**请求是有意为之：拆成多次调用会留下「配置写了但没装完」的中间态，
而初始化状态的判定是双保险 —— 中间态会被判成「未初始化」，等于把闸门重新打开，
留出被抢先建管理员的窗口。
中途失败可以原地重试（幂等）：管理员已存在且本身就是管理员时会跳过创建，
直接把标志补上。

> 「未初始化」判定在**数据库不可用**时也有讲究：改数据库配置这类操作在数据库不可用时放行
> （站点本来就是坏的，正需要向导来救），而建表、创建管理员仍然 fail-closed。
>
> **「数据库不可用」= 连不上 或 认证不过**：
>
> | 类别 | 典型错误 | 判定 |
> |---|---|---|
> | 连不上 | `ECONNREFUSED` / `ETIMEDOUT` / `ENOTFOUND` / 连接池没建起来 | 算「不可用」→ 放行改配置 |
> | 认证不过 | `ER_ACCESS_DENIED_ERROR`(1045，账号密码错) / `ER_DBACCESS_DENIED_ERROR`(1044，账号对该库没权限) | 算「不可用」→ 放行改配置 |
> | 判定 SQL 跑不通 | `ER_BAD_FIELD_ERROR` / `ER_TABLEACCESS_DENIED_ERROR`(1142，表级权限不足) | **不算**「不可用」→ fail-closed |
>
> 认证失败必须算「不可用」：全新部署时仓库不带 `.env`，进程按默认值连 `root@localhost`
> 且不带密码，MySQL 必然回认证失败。若把它当成「连上了但查询失败」，向导连 `.env`
> 都写不出来，安装流程当场就卡死。
>
> 反过来，「连得上、认证也过了，只是判定安装状态的那条 SQL 跑不通」一律 fail-closed：
> 这时站点多半是装好的，放行改配置等于允许把一个装好的站点重新指向别的库。

### 未初始化时页面也会被拦

判定为「未初始化」之后，**不只是 API 返回 503**，静态直出的页面同样会被引导到 `/init`：

| 请求 | 未初始化时的响应 |
|---|---|
| `GET /`、`GET /xxx.html` | **302** → `/init` |
| `GET /css/**`、`GET /js/**` 等静态资源 | 200（照常提供，页面本身要靠它们渲染） |
| `GET /init` | 200（向导页面本身） |
| 其余 API | 503 `{ error: '数据库当前不可用', initUrl: '/init' }` |

> 这一层拦截是必要的：静态文件由 `express.static` 直出，如果不管它，
> 未初始化的站点首页会返回 **200 + 空壳 HTML**，运维看着「页面能打开」就会以为站点正常，
> 实际上里面的 API 全是 503 —— 故障现场会被误判成「站点正常、只是数据没内容」。
>
> 数据库**不可用**（连不上 / 认证不过）时同样跳 `/init`：站点本来就是坏的，
> 需要向导来救，此时把访客留在首页只会让人对着空壳页发呆。
>
> 判定「无法确定」（例如判定 SQL 本身跑不通）时**放行**页面 —— 那多半是个装好的站点，
> 不该因为判据读不出来就把首页也锁死。

### 数据库不可用时怎么办

服务器启动时如果数据库不可用，**不会退出进程**，而是降级启动：

- `/init` 与 `/api/init/*` 照常可用（控制台会提示「站点尚未完成初始化，请打开 /init 继续」）；
- 其余依赖数据库的接口统一返回 **503** `{ error: '数据库当前不可用', initUrl: '/init' }`；
- 修好连接后重启（或在向导里保存配置）即可恢复。

### 存量站点升级到本版本

升级前的站点，`.env` 里没有 `INITIALIZED` 这一行。新判定要求它存在，
所以**必须在重启服务之前**手工补上：

```ini
INITIALIZED=True
```

同时把旧部署遗留的 `data/db-config.json` 里的 `DB_*` 参数手工搬进 `.env`，
确认无误后删掉那份 json —— 新版本启动时既不读它也不删它。

补不补这一行的区别很实在：缺了它，站点会被判定成「未初始化」，
全站跳转到 `/init`，Init 接口也会重新打开。
服务启动时会在控制台打印醒目告警提示这件事。

反向情况（有管理员但没标志）也能靠向导补救：走一次完整初始化流程，
管理员那一步会识别出「该用户名已是管理员」并跳过创建，只把标志补上。

> **恢复路径只允许「认领」已有管理员，不允许再造一个。**
> 库里已经有管理员就说明站点其实上线过，这时用**新用户名**跑向导会被 409 挡掉 ——
> 否则等于给一个已经上线的站点开了「随便塞管理员」的口子。
> 正确做法：第 2 步填你现有的管理员用户名，或直接在 `.env` 里补一行 `INITIALIZED=True` 后重启。

### `.env` 里有什么

注意：**`.env` 是 Init 向导的产物**，仓库里只留 `.env.example`（模板与说明）。
向导最后一步点「开始初始化」时，会生成 `.env`（权限 0600），里面是：

| 键 | 来源 |
|---|---|
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` | **你填的**（向导负责建库，也负责建表） |
| `SESSION_SECRET` / `CRON_TOKEN` | **机器随机生成**（沿用已有 `.env` 里的旧值，不顺手作废会话） |
| `PORT` | 沿用当前进程端口 |
| `INITIALIZED` | **状态标志** —— 先写 `False`，向导最后一步置为 `True` |

写入后**当场生效**（连接池立即切换），但会话密钥与 session 存储池在启动时绑定 ——
向导最后一步会提示重启一次。旧的 `.env` 会被备份成 `.env.bak`；新配置连不上时会自动回滚。

> **`.env` 是数据库连接参数的唯一存放处。** 旧部署遗留的 `data/db-config.json`
> （第二处明文凭据副本）**不再自动接管** —— 启动时既不读它也不删它。
> 请手工把里面的 `DB_*` 搬进 `.env`，确认无误后删掉那份 json。
>
> 收口之后配置来源只剩两态：`env`（来自 `.env`）与 `default`（`.env` 尚未生成）。
> 不再存在「来自 json 文件」这一态。

`.env` 里**刻意不写**的键：`MCP_TOKEN`（主令牌改由后台「系统设置 → MCP」生成/轮换，
存在数据库里）。`INIT_TOKEN` / `SETUP_TOKEN` 属于**已移除**的 Init 令牌机制，
不再被读取，也不会出现在 `.env` 里。

**保存时不会误伤其它键**：受管键之外的原有键（如 `PAYPAL_WEBHOOK_ID`、
`MCP_ALLOWED_HOSTS`、`DB_COPY_ALLOWED_HOSTS`）会被**整行原样**搬到文件末尾的
`Preserved` 段；受管键里**值没变**的那些（如沿用的 `SESSION_SECRET`）也保留原始行。
全程不做「解析 → 重新序列化」的往返，因此一个字节都不会变。
注释掉的键不会被「复活」（注释即未配置）。

## 公开接口（无需认证）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/install` | 提交安装注册 |

> 详见 [MCP 端点 §3.4](mcp-endpoint.md#34-产品一律是草稿上架必须人工) 与 [§3.5](mcp-endpoint.md#35-草稿产品的下单闸门)。
